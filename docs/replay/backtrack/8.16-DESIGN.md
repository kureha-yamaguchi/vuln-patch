# 8.16 — Passing-suite behaviour delta as a fact. DESIGN NOTE ONLY.

**Target station.** A new evidence generator, station-6 peer of
`relations/relation_screen.py`. Consumer: judge evidence assembly in `run.py`.

**Failure mode it addresses.** The separating-fact study's honest close: the
accusation side may need a different KIND of evidence than we collect at all.
Cycle 8 tested four dimensions of *presentation* — delivery, placement,
questioning, judge model — and got four negatives. This item exists because
those negatives point at the evidence set, not at the reviewer.

## The gap, stated concretely

Our pipeline anchors on the **failing** test and on generated harnesses. It
never uses the project's **passing** suite as a behavioural anchor. That is a
whole authority we hold and do not read.

PATCH-SIM (ICSE 2018) is the published form: run the existing tests on the buggy
and patched builds and measure how much the *passing* tests' execution behaviour
changes. Correct patches barely disturb passing-test behaviour; overfit patches
disturb it more.

**Why it is admissible.** It uses only the buggy build and the project's own
tests — authority ranks 1 and 2. The developer fix never appears. No firewall
issue.

## It enters as a FACT, never a gate

A later replication (ASE 2020, *how far are we?*) found **moderate**
discriminative power. Moderate is enough to inform a judgement and nowhere near
enough to decide one.

So the output is a computed fact in the evidence block — "this patch changes the
behaviour of N of M passing tests" with the measurement stated — and it never
becomes a gate, a drop condition, or a threshold. Cycle 8's own history is the
argument: every mechanism that turned a moderate signal into an automatic
decision cost more than it bought.

## What must be priced

**1. Trace-capture cost on Defects4J-scale suites.** This is the item's main
risk and it is not small. Capturing per-test execution behaviour across a full
project suite, twice (buggy and patched), for every leg, is a different order of
cost from anything else in the pipeline — our current per-leg work is fuzzing a
handful of generated harnesses. If the cost is prohibitive the honest answer is
to sample the suite, and sampling changes what the number means, so that must be
designed rather than discovered.

**2. The moderate power, honestly carried into the wording.** The fact's text
must state that this signal is moderate. A fact that reads as decisive when the
underlying measurement is moderate is exactly the over-claim that cycle-2b's
Spec I had to undo.

**3. Interaction with the family-duty boundary.** This is the substantive design
problem. **Legitimate fix propagation also moves passing-test behaviour.** A
correct patch that genuinely changes a shared code path will disturb passing
tests, and the mechanism would score it as overfit-shaped. The family-duty
boundary already distinguishes "the defect's own observable" from "something
else", and this mechanism needs the same distinction applied to the delta: a
behavioural change *inside* the defect's family is expected and must not count
against the patch; a change *outside* it is the signal.

Without that split the fact would systematically accuse correct patches that fix
things properly — the worst possible failure direction for a pipeline already at
its accusation ceiling.

## Guard plan, set BEFORE mechanism

This fact pushes toward **accusation**. Guard: the **38-row correct-dismissal
fixture**. A correct patch whose legitimate propagation moves passing-test
behaviour is precisely the row that would flip, so this guard is not a formality
here — it is aimed at the mechanism's known weak point.

Secondary: 67-row genuine catches, for the opposite damage.

As with 8.4 and 8.2, neither archived population carries this fact and neither
can, so both demonstrate **regression only**. The real guard is a live run.

## Sequencing

**After 8.2.** Both are new evidence generators aimed at the same failure class;
running them together makes neither attributable. 8.2 is the better-grounded of
the two (its authority screen is exact; this one's signal is statistical), so it
goes first.

## Done when

This note exists with its cost risk and its family-duty interaction named. Build
decision is the user's, and should probably wait on 8.2's outcome.
