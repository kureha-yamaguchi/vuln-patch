# 8.4 — Raw-value recording: compare normalized, RECORD raw

## The defect, stated generally

**A transformation applied for comparison must not destroy the original.**

Concretely: `prompts.py:313` instructs every check whose expected value is code or
formatted text to *"never compare raw strings — normalize BOTH sides first
(collapse all whitespace runs)"*. That instruction is correct for the comparison
and wrong for the record. The fired message then reports only normalized values,
so the setup-divergence dismissal rung — which asks whether the fired value equals
a value the failing test pins — compares a normalized derivative against the
test's raw literal. They can never be equal, so the rung is **structurally dead**
for every normalizing check.

Measured reach: **10 of 60 accepted harnesses (17%) normalize before comparing**,
and only 2 of those 10 report a raw value.

This is why Closure-62 was unreachable. Its test pins
`...ERROR - error description here\nassert (1;\n          ^\n` while the alarm
reports `lhs=javascript/complex.js:1:ERROR-errordescriptionhere`. Same content,
whitespace stripped — and Closure-62's defect **is** a whitespace defect, so a
comparison loose enough to match them would be wrong for the wrong reason.

## The change

Keep comparing normalized. Additionally record the pre-normalization value.

**Named keys, not positional.** The downstream consumer is the extractor for the
setup-divergence rung, and after this week the idea of an extractor silently
reading the wrong field should trip every alarm we have just installed. Positional
values (`expected=… actual=…`) give the extractor no way to tell which form it is
holding; a mis-read would be **fail-open and invisible** — standing rule 15's
exact family, in a component whose failure mode is "the rung stays dead and
nobody notices".

Format:

```
[oracle:<id>] semantic mismatch: <what differed>
  expectedNormalized=<…> actualNormalized=<…>
  expectedRaw=<…> actualRaw=<…>
```

The `Raw` keys are emitted **only** when normalization was applied, so their
absence is meaningful rather than ambiguous: no `…Raw` key means no
normalization happened, not "normalization happened and we forgot".

## Validation, measured alone

1. **Compliance smoke, ~20 generations.** Do fired messages from normalizing
   checks actually carry both forms, under named keys? This is a prompt change,
   so compliance is the thing that can fail — not correctness.
2. **Extractor extension, then cases228 measured alone.** No verdict may flip
   *except* via newly-possible legitimate matches. Closure-62's rows are the
   named target: today all 12 compare `unknown`; success is any movement to
   `matches` or `differs`.
3. **Guard:** the setup-divergence rung pushes toward DISMISSAL, so its guard is
   the 67-row genuine-catch fixture. A raw-value match that voids a genuine catch
   fails the change.

## Explicitly NOT bundled

The Math-104 codegen-hygiene line — *a check must not assert a tolerance tighter
than the implementation's own documented default* (its harness compared at
`10e-15` against a documented `DEFAULT_EPSILON = 10e-9`) — would ride this same
prompt change for free.

It is deliberately held back. 8.4's validation must certify that **no verdict
flips except via newly-possible legitimate matches**, and that claim gets strictly
harder to make with a second prompt change in the same diff. The hygiene line's
payoff is fewer wasted firings, and 8.18 measured that class as *merited
dismissals* rather than verdict errors — so it buys nothing that justifies
muddying this measurement. Recorded as a later-batch candidate.

## TWO DEPENDENCIES THE DESIGN MISSED, found before building the extractor

Both discovered by testing the intended consumer rather than assuming it.

### 1. The rung's comparison cannot read what 8.4 produces

Normalizing checks are, by the prompt's own definition, over **code or formatted
text** — so their values are strings. The setup-divergence rung compares via
`fired_value_vs_trusted`, which is **numeric-only** (fix (ii), the string
comparison, was measured a wash and deferred).

Verified with Closure-62's exact shape carrying full `expectedRaw`/`actualRaw`
keys: `_fired_numbers` returns `[]`, and the verdict is still `unknown`.

**So extending the extractor alone would deliver raw values to a consumer that
cannot read them** — a shipped no-op, the fourth mechanism this cycle caught inert
before it shipped.

What this needs is a comparison scoped to raw-vs-pinned, and that is *not* a
revival of fix (ii). Fix (ii) compared arbitrary tokens on any evidence and was a
wash. This compares **the raw output against the literal the test pins**, which is
the exact question the rung is supposed to ask and is answerable exactly rather
than approximately. It is narrower, better-grounded, and needs its own measurement
— against the **67-row genuine-catch guard**, since the rung pushes toward
dismissal.

### 2. `cases228 measured alone` cannot validate the extractor half

**0 of 228 recorded rows carry a `Raw=` key**, and none can: the prompt change
shipped today, and no archived case can contain a field that did not exist when it
was recorded.

So cases228 can confirm **no regression** (nothing flips on old data) but cannot
demonstrate the intended gain. The gain can only be measured on **newly generated**
harnesses — i.e. the compliance smoke's output is not just a compliance check, it
is the *only* corpus in which the extractor can be validated at all.

**Revised sequence for the remainder of 8.4:**

1. compliance smoke (~20 generations) — do harnesses emit the named keys?
2. build the raw-vs-pinned comparison, scoped to the rung
3. validate it **on the smoke's output** (the only data with raw keys)
4. run cases228 as a **regression** check only — nothing may flip on old data

### Step 3's guard claim, scoped honestly

The first draft of this sequence said "validate against the 67-row guard". That is
**structurally vacuous, for the same reason cases228 is regression-only** — and I
wrote it one paragraph after diagnosing that exact flaw for cases228.

The archived guard rows cannot carry `Raw` keys either. So on all 67 the new
comparison is a no-op, and the guard would "pass" **without ever being
exercised**: a guard evaluated on inputs that cannot reach it. Rule 15's family,
fifth instance this cycle.

What each population can actually claim:

| population | what it proves |
|---|---|
| archived 67-row guard | **regression only** — the comparison does not fire where `Raw` keys are absent. Worth having; that is all it proves. |
| compliance smoke (~20 generations) | first evidence that the keys are emitted, and the first inputs on which the comparison can fire at all. **20 generations over two legs is not a guard population.** |
| the next live suite | **the real guard** — read per-event under smoke-before-pair discipline, before the rung's verdict surface is trusted. |

So no "guard passed" statement may be made about the dismiss-pushing risk until a
live suite has exercised it. Until then the comparison ships as
**observably-inert-on-old-data**, which is a regression claim, not a safety one.

## Honest expectation

This makes a dead rung live for ~17% of checks. It does **not** promise verdict
movement: 8.14c showed Closure-62's dismissal needs the fired value to match a
pinned value, and raw recording only makes that comparison *possible*. Whether it
then matches is a separate question this change does not answer.

# 8.4 compliance smoke — RESULT: 100%. (The 38% below was an artifact; struck.)

`c84_20260801_174840`, git `298d9d9`, two formatter/printer legs.

## CORRECTED: compliance is 100%. The 38% was measured in the wrong place.

**12 of 24 fired-alarm records are visibly truncated**, ending in an ellipsis. The
count below read those truncated records and scored an alarm non-compliant
whenever its `Raw` keys fell past the cut. Measured at **source level**, which
truncation cannot affect:

```
alarms reporting a Normalized value : 46
...also reporting both Raw keys     : 46
compliance                          : 46/46 = 100%
```

The lint agrees independently — 0 violations across all 18 recovered harnesses,
0 false flags on compliant ones. Two methods that cannot share this failure mode
(source counting cannot see truncation; the lint reads harness text, not records)
give the same answer.

**Consequences:** the authorized second iteration is withdrawn unused (~400k not
spent); the prompt half of 8.4 is done; the lint still ships, not to fix
compliance but so absence-of-`Raw` is trustworthy *by construction* for the
extractor's three-state read.

**The error, named:** I measured compliance in the *record of* the alarm rather
than in the alarm itself — and quoted a visibly truncated sample (`actualRaw=x--…`)
in my own report without registering the ellipsis. Rule 8's other direction: four
earlier cycle-8 miscounts *inflated* by matching text that merely mentioned the
thing; this one *deflated* by reading a truncated copy of it.

## The original (struck) reasoning, kept for the record

A first count said 180 `expectedRaw` and 204 `actualRaw` occurrences — **that was
contaminated**. The grep matched my own prompt text (which contains the key names)
and the Java source that constructs the message. Same shape as the
`VERDICT: SOUND | UNSOUND` template inflation.

Counting only **actual fired alarm messages**:

```
fired alarms                                25
  normalized AND raw   (compliant)           5
  normalized, NO raw   (violation)           8
  raw only                                   1
  neither (non-normalizing check)           11

compliance among eligible alarms:  5/13 = 38%
```

**38% is not a dependency you can build on.** The extractor would read raw values
on roughly a third of normalizing checks and silently see nothing on the rest —
and "silently see nothing" is precisely the failure mode this cycle has spent five
instances learning to distrust.

## But the mechanism is right, and one alarm proves it

```
[oracle:boundary-negative-zero] semantic mismatch:
  expectedNormalized=x--0.0  actualNormalized=x--0.0
  expectedRaw=x- -0.0        actualRaw=x--0.0
```

The **normalized forms are identical** and the **raw forms differ** — and that
difference (`x- -0.0` vs `x--0.0`) is exactly Closure-38's defect, the missing
separator space. Normalization erased the bug; the raw record preserved it.

That is 8.4's entire thesis, demonstrated live on the first run. The design is
sound. The compliance is not.

## What follows

1. **Do not build the extractor against 38% compliance.** It would ship a
   consumer whose input is present a third of the time, with absence
   indistinguishable from "this check didn't normalize".
2. **The prompt instruction needs strengthening before the extractor is worth
   building** — most plausibly by making the Raw keys part of the *required
   message format* rather than an additional instruction attached to the
   normalization paragraph, so omitting them reads as malformed rather than as a
   choice. That is a second prompt iteration, and it needs its own compliance
   smoke.
3. **Cost note:** each compliance iteration is ~300–500k. Two more iterations to
   reach usable compliance is comparable to the 8.1 experiment's cost, which is a
   real trade to weigh rather than assume.

**8.4 status: prompt change shipped and demonstrably correct in mechanism;
extractor NOT built; compliance measured at 38% and insufficient.** The honest
close is that 8.4 is one iteration short, not done.

# 8.4 — the raw-vs-pinned comparison: BUILT AND MEASURED

`evidence_facts.raw_value_vs_pinned`, wired as the precedence branch of
`fired_value_vs_trusted`. 21 tests. Full suite 589 → 610 passed, 7 skipped.

## What it does

Compares the alarm's pre-normalization `actualRaw=` value against the literals
the failing test pins, **exactly** — no tolerance, no trimming. The one
transformation is decoding Java escapes on the **pinned side only**, so `\n` in
test source and a newline in a runtime string can meet. Decoding is not
normalization: nothing is collapsed or discarded, which is the point, since the
checks this serves are the ones whose defects ARE whitespace defects.

**Observed field only.** `expectedRaw` is the check's own reference and for a
lifted test is frequently derived from the very literal being compared against —
comparing it would match by construction and dismiss every lifted firing. That
is the trap `_observed_numbers` was narrowed to avoid, reached from the string
side instead of the numeric one. Pinned by test.

## The asymmetry it is built around

`matches` is the only verdict that licenses a dismissal, so every uncertainty
resolves away from it:

| situation | verdict | why |
|---|---|---|
| no `actualRaw=` key | `unknown` | inert on everything written before 8.4 |
| mis-captured value | never `matches` | `matches` needs exact equality; over- and under-capture are both fail-safe in the dismissal direction |
| capture ended at an unknown key | `unknown` unless exact-equal | may have swallowed metadata, or may have cut a value that legitimately contains ` x=1` |
| multi-line raw, no exact hit | `unknown`, **not** `differs` | a possibly-truncated capture does not support the positive claim "differs from every value the test pins" |

The cost is missed dismissals. That is the direction this rung should fail in:
the population it acts on is findings that would otherwise be kept.

## A defect the smoke's real alarms caught in the first draft

`actualRaw=x--0.0 parseErrorCount=0` — real alarms append their own metadata
keys after the raw pair. The first parse stopped only at the four 8.4 keys, so
it captured `x--0.0 parseErrorCount=0` as the value. Found by running against
archived alarms rather than synthetic ones, which is the corollary earning its
keep a second time this batch.

## CLAIM 1 — no regression. Measured.

```
  cases228             rows= 228  verdicts changed=0
  correct-dismissals   rows=  38  verdicts changed=0
  genuine-catches      rows=  67  verdicts changed=0

TOTAL archived rows=333  carrying actualRaw= : 0  verdicts changed: 0
```

Zero rows carry the key **and none can** — the field postdates all of them. So
this is a regression claim and nothing else. It is **not** a safety claim about
the dismissal direction.

## CLAIM 2 — mechanism-correct on new data. Measured, with its limit stated.

The only corpus with raw keys is `c84_20260801_174840`. Alarm-scoped extraction
(so prompt text naming the keys cannot inflate it):

```
fired-alarm records (alarm-scoped): 24
  carrying actualRaw=            : 5
  ...of those, TRUNCATED records : 2
```

On leg `02_patch1-Closure-38-SequenceR_o`, pinned literal `x- -0`:

```
oracle                             OLD(numeric)  RAW       NEW(shipped)
--------------------------------------------------------------------------
boundary-negative-zero             matches       differs   differs
minus-negative-zero-exact-print    unknown       differs   differs
seed-reparse-validity              unknown       differs   differs
negzero-seed-groundtruth           matches       differs   differs
negative-integer-spacing           differs       differs   differs
```

**Two alarms move `matches` → `differs`, and that is a correction.** The leg is
`_o` — a FAKE patch, where every alarm should be KEPT. The `-0.0` in those
messages is within the rounding floor of the `0` inside `x- -0`, so the numeric
comparison answered `matches`: the one verdict that instructs the judge to
dismiss. The actual strings differ by exactly the missing separator space, which
IS Closure-38's defect.

**The limit, stated precisely.** No dismissal was actually lost in that run:

```
$ grep -c "\[trigger-test lift\] this oracle lifts" trace.md
0
```

The lift detector never fired on that leg, so no note reached the judge. This is
a **latent** false dismissal — demonstrated on real data, now closed — not an
observed lost catch. Three alarms also moved `unknown` → `differs`, which
delivers "test-passage does not exonerate it" where the rung previously said
nothing.

## What is NOT claimed

* Not that any verdict improves. 8.14c showed the dismissal needs the value to
  match a pinned value; this only makes the comparison possible and correct.
* Not that the dismiss-pushing risk is guarded. 5 alarms on 1 leg is not a guard
  population, and all three archived guards are inert here by construction.
* **The real guard is the next live suite**, read per-event under
  smoke-before-pair discipline, before this rung's verdict surface is trusted.

Status: **observably-inert-on-old-data + mechanism-correct-on-new-data.**
Neither is a safety claim.
