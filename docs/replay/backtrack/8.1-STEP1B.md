# 8.1 step 1(b) — the fail-open sentinel. A real hole, found before spending.

The plan's step 1 requires, before any spend: *"verify `reask_verdict_usable()`
recognizes THIS deployment's error/sentinel strings (a silently fail-open judge
is the July-15 bug; add its error format to the sentinel list if absent). Commit
this check before spending."*

Done. The check found a hole — not in the sentinel list, in the code that is
supposed to produce the sentinels.

## What `reask_verdict_usable` is for

`RelationVerifier.verify` fails open on an LLM error or an unparseable response.
`reask_verdict_usable` exists so a caller can tell a real verdict from that
fail-open, and keep the ORIGINAL verdict rather than adopt a manufactured one.

## The hole

Two producers used the idiom `why or "<sentinel>"`, which **substitutes** the
model's own text for the sentinel whenever the response carried a `WHY:` line.
So a response with no parseable verdict, but any WHY line, was reported USABLE.

Measured before the fix:

```
response shape             parse ->                           usable?
------------------------------------------------------------------------
well-formed UNSOUND        (False, 'counterexample x\nCITATIO') True
well-formed SOUND          (True , 'fine\nCITATION: NONE'    ) True
NO verdict, no WHY         (True , 'no verdict parsed; keepi') False
NO verdict, WHY present    (True , 'the harness looks unusua') True     <-- hole
preamble then WHY only     (True , 'unclear'                 ) True     <-- hole
```

Both producers:

* `_parse` — `why or "no verdict parsed; keeping finding"`. Fails open to KEEP,
  so a suppressed sentinel makes an unparsed response read as a real SOUND.
* `family_duty`'s inline duty parse — `why or "no DUTY verdict parsed"`. This
  branch **DROPS**, so a suppressed sentinel there makes an unparsed response
  read as a deliberate "duty does not apply" — the direction that costs a
  finding.

## Why this belongs to 8.1 and not to general hygiene

**It is model-swap sensitive.** The answer format is `VERDICT:` first, then
`WHY:`. The incumbent follows it, so an unparsed response almost always carried
no WHY either and the sentinel appeared *by luck*. A model that writes a
preamble, reorders the fields, or is truncated after WHY would have been
silently fail-open on every such call — and the swap experiment reads per-case
flips, so manufactured verdicts would have been scored as model differences.

This is the July-15 bug's exact shape: a judge that fails open while looking
like it answered. It is also rule 15 once more — a guard whose inputs can be
suppressed is fail-open while appearing armed. Sixth instance this cycle.

## The fix

The sentinel is now emitted **unconditionally**, with the model's own text
appended rather than substituted (`"no verdict parsed; keeping finding — model
said: <why>"`). Diagnostic value preserved, detectability restored.

## The half of step 1(b) that needed no probe

**A new deployment's error strings cannot evade the check**, because the
exception is wrapped into our own prefix:

```python
except Exception as e:
    verdicts.append((True, f"verifier error ({e}); keeping finding"))
```

The sentinel keys on `verifier error`, our wording — not on the provider's error
text. So the "add its error format to the sentinel list if absent" clause has
nothing to add for the ERROR path. The exposure was never the provider's
strings; it was our own suppression. Pinned by test.
