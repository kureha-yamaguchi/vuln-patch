# 8.2 — Reimplementation as evidence. DESIGN STUDY ONLY; nothing built.

**Target station.** A new evidence generator in the execution layer, a peer of
`relations/relation_screen.py`. Its output threads into evidence assembly in
`run.py` as one more computed fact, next to `disputed_computation_fact`.

**Failure mode it addresses.** Accusations that rest on a *misremembered
contract* — the Math-65 class. These are disputes about what correct behaviour
IS, and cycle 8 established they survive every delivery-side fix: they survived
being delivered, being placed next to the firing, and being asked about
narrowly. Four independent dimensions, four negatives. If they are reachable at
all, it is with a different KIND of evidence, not a better presentation of the
evidence we already have.

## 1. Mechanism

For a disputed observable — detected exactly the way `disputed_computation_fact`
already detects one, i.e. the firing names a method whose body is shown —
generate an independent implementation **from the documentation**, never from
the patched source, and run it on the same inputs.

The generated-from-intent constraint is not a stylistic preference. A reference
derived from the code under test inherits that code's bug and then agrees with
it, which is the failure that makes the whole idea worthless. Differential
Prompting (ASE 2023) reports the same constraint from the other direction: 75%
success at finding failure-inducing inputs when the reference comes from
inferred intent, against 28.8% for direct prompting.

## 2. THE AUTHORITY SCREEN — this is the entire design

A generated reference is not an authority. It is a guess by the same kind of
model that produced the accusation, and it can misremember the same javadoc the
accusers misremember. **Same-model risk is the central threat and the screen is
the only defence.**

So: **validate the reference against the BUGGY build, on observables the defect
does not touch.** The family-duty boundary decides "does not touch" — it already
exists and already answers exactly that question.

* reference disagrees with the buggy build off-defect → **discard it, emit
  nothing.** Not a weaker fact, not a hedged fact. Nothing.
* reference agrees off-defect → it has demonstrated it reproduces the
  incumbent's semantics where the bug is not involved, and only then may it
  generate the fact:

  > the patched output disagrees with a documentation-derived reference that
  > matches the buggy build's semantics everywhere the defect does not reach.

This keeps the mechanism inside the label-independent authorities. The reference
is checked against the buggy build (authority rank 2) and built from
documentation (rank 3). The patched artefact is never an authority about itself —
on a fake patch it *is* the defect.

Poracle (TOSEM 2023) is the published form of this same authority: preservation
conditions describing behaviour a patch must keep from the original program.
Nothing to build from it; it is evidence the approach class holds up.

## 3. The mirror canary, specified as a test

Fake patch + correct check → **the reference must side WITH the check, not with
the patched code.**

This is the one test that distinguishes a working mechanism from an elaborate
way of agreeing with whatever it is shown. It runs before any reach measurement,
and a mechanism that fails it is dead regardless of how well it scores
elsewhere.

## 4. Reach, measured — not estimated

The trigger is already implemented, so its reach is a fact rather than a guess.
Measured on cases228:

```
  rows total                                      : 228
  rows where the firing NAMES a shown method      :  58  = 25.4%
  by label: overfitting 34 · correct 24
  distinct bugs covered: 9
  Chart-19 Chart-7 Lang-41 Lang-50 Lang-60 Math-104 Math-30 Math-65 Math-73
```

**Read this honestly: 25.4% is the reach of the TRIGGER, and it is an upper
bound on the reach of the mechanism.** Every row that passes the trigger must
then survive reference generation *and* the buggy-side screen. The screen is
designed to discard aggressively, so the delivered-fact rate will be materially
lower, and no number here should be quoted as the mechanism's reach.

The 24 `correct`-label rows in the trigger population matter as much as the 34
overfitting ones: those are where a mechanism that fires wrongly would
manufacture false accusations.

**Price:** one reference-generation LLM call per disputed observable, plus the
screen's execution cost on the buggy build, on up to ~25% of firings. Neither
is priced in tokens here because the screen's discard rate is unknown until
built, and inventing a number would be worse than saying so.

## 5. Prior art to reuse rather than reinvent

`plan-history.md` PART 1, **P4.2 (split certifier probe)**. Its lesson is
directly load-bearing here: *a mechanism beats an instruction.* Half the
certifier's "no difference found" answers were wrong, and every one came from a
prompt that asked the model to "print EVERY public observable" — which it simply
did not do. The fix was to split the job: the model constructs interesting
inputs and call sequences, and **fixed code of ours** then enumerates and prints
every public no-argument observable before and after each step.

The reference-implementation generator should be built the same way. The model
writes the reference; **our code**, not the model, decides which observables get
compared and prints them all. A reference that is only compared on the
observables the model remembered to check has the P4.2 bug wearing new clothes.

Also reusable: the certifier's divergence-kind classifier, including its WEAK
kinds (`value_ulp`, `exception_generic_latent`). A divergence of a weak kind is
not the same evidence as a real disagreement and must not be reported as one.

## 6. Dependency

Needs **8.3** (buggy-side observed values). Without it the screen has nothing to
compare the reference against, so 8.2 cannot be built first — and a "screen" that
cannot run is rule 15's shape: armed-looking and fail-open. 8.3 is the
precondition, not an optimisation.

## 7. Scope note — the dismissal side, deliberately NOT part of this design

The same buggy-validated machinery could in principle ground dismissal-side
hypotheticals: the "a correct implementation could return X" claim, which is the
measured drift-kill signature and was **wrong in 4 of 6 measured instances**. A
grounded version would test whether such an implementation actually exists rather
than accepting the assertion.

Recorded as a design consideration only. If it is ever built it is a **separate
mechanism with its own guard**, because it pushes the opposite way: it argues
*toward keeping* a dismissal, so its guard population is the correctly-dismissed
firings on correct legs (the 38-row fixture), not the genuine catches. Cycle 8's
standing presumption applies — any fix aimed at one direction is presumed to
damage the other until measured against the opposite guard.

## Guard plan, set BEFORE any mechanism

The fact pushes toward **accusation** (it tells the judge the patched output
disagrees with a validated reference). So its guard is the **38-row correct-
dismissal fixture**: a fact that overturns those manufactures false accusations,
which is the failure that the ≤5-accusation bar cannot absorb.

The 67-row genuine-catch fixture is the *secondary* guard, checked for the
opposite damage.

Both are archived populations and neither carries this fact, so — exactly as with
8.4 — they can demonstrate **regression only**. The real guard is a live run.
Stating that now, before the mechanism exists, so it cannot be claimed later.

## Done when

user decides build / no-build. **No code.**
