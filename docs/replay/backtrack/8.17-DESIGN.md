# 8.17 — Deterministic invariant mining as a second rule source. DESIGN NOTE ONLY.

**Target station.** `relations/relation_synth.py` (station 2) — a second,
DETERMINISTIC candidate source feeding the same screen → replay machinery that
LLM synthesis already feeds.

**Failure mode it addresses.** The invention lottery, at its root. Measured
family behaviour across rolls: **RELIABLE 6 / COIN-FLIP 4 / INVENTS-BUT-NEVER-
FIRES 4.** Lang-63's winning family was present in one roll and absent the next.

The structural point: **LLM synthesis is currently the only candidate source,
and it re-rolls per leg.** No amount of re-rolling fixes a lottery — it *is* the
lottery. A deterministic source produces the same candidates for the same leg
every time, which is a different kind of fix from making the existing source
better.

## The admissible half of Invalidator, and the half that is firewalled

Invalidator (TSE 2023) infers likely invariants from executions and flags a
patch that violates correct-version invariants or preserves the buggy version's
error behaviour.

* **Firewalled:** their correct-version half. It uses the developer patch. Not
  available to us, not negotiable.
* **Admissible:** invariant mining over **buggy-build executions only**.
  Daikon-style, deterministic, same leg → same candidates → every roll.

The firewall line here is sharp and worth restating because the paper's framing
invites crossing it: we may mine what the *buggy* program does, and we may never
mine what the *fixed* program does.

## The mined54 precedent — the constraint that shapes the whole design

A mined-oracle flood **cost Lang-7's true positive**. That is the measured
precedent and it dictates two hard rules:

1. **Mining feeds the existing screen; it never bypasses it.** Mined candidates
   are candidates, with exactly the standing of LLM-proposed ones. No mined
   invariant reaches a harness without passing the same screen.
2. **Survivors compete for the same `--synth_max_rules` slots.** They do not get
   their own budget. A mined flood that crowds out the invented family which
   would have caught the bug is the mined54 failure repeating, and a separate
   budget is precisely how that happens.

## What must be addressed before building

**1. Template reach on our observable shapes.** Daikon's templates were designed
for scalar and container invariants. Our observables are frequently formatted
text, floating-point results with tolerance, and exception identity. The honest
question is how many of our firing shapes any invariant template can express at
all — and if the answer is "few", the mechanism is narrow regardless of how
deterministic it is. This is measurable offline against the existing corpus and
should be measured before anything is built.

**2. Interaction with 8.9.** Both are anti-lottery mechanisms; **they have never
been measured together and must not be shipped together.** If both land at once,
neither's contribution is attributable — the same confound that made bundled
fixes (i) and (ii) look net-positive when measured jointly and split 1/0 and 0/1
when measured alone.

**3. The gate, re-set by 8.14c (2026-08-01).** Archival reading **cannot** decide
this. The invented-vs-too-weak boundary is not drawable from traces: a family
that was proposed and screened out leaves the same shadow as one never proposed.
So the gate is a **live A/B, priced against the measured class** — invention is
the minor station at 1 confirmed + 3 ambiguous of 14 misses.

That is a weak justification for a build of this size, and this note says so
plainly rather than letting the mechanism's elegance carry it.

## Design constraint inherited from the 8.14b retraction

**Family identity in this mechanism must be defined SEMANTICALLY — by asserted
property — never by generated name string.** Same constraint as 8.9, same
reason: generated names have no stable vocabulary, and a mechanism that
deduplicates mined candidates against invented ones by name will believe it is
avoiding duplication while doing nothing.

Concretely, a mined invariant and an LLM-proposed check assert the same family
when their (observable, relation-kind, argument-role) triples match.

## Guard plan, set BEFORE mechanism

More candidate rules → more checks → more firings → pressure toward
**accusation**. Guard: the **38-row correct-dismissal fixture**, plus the
mined54 precedent's own lesson measured directly — does the mined pool crowd out
a family that catches something? That second question is answered against the
**67-row genuine-catch fixture**, because slot competition damages recall.

Unusually for cycle 8, this mechanism plausibly damages **both** guards at once:
accusation pressure from the extra firings, recall loss from slot competition.
That is a reason for caution, not a reason to skip either measurement.

## Done when

This note exists. **Build only behind a live A/B**, and only after the offline
template-reach measurement says the mechanism can express our observable shapes
at all — that measurement is free and should happen first.
