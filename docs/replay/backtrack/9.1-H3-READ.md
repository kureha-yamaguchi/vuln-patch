# 9.1 — the H3 five-case read. Four correct, one wrong, and the wrong one is
# about to get worse.

Five H3 rejections across 120 archived legs (final30A/B, pairA8/B8). Each
re-judged by running the shipped matcher on the recorded values.

## The four that are right

| # | leg | observed | verdict |
|---|---|---|---|
| 1 | Closure-62-c (July A) | `javascript/complex.js:1:ERROR-errordescriptionhere` | correct |
| 2 | Closure-62-c (July B) | same | correct |
| 3 | Closure-62-c (July B) | `...error description here\n expected=...` | correct |
| 5 | Math-68-o (pair B) | `4.948952097518721 tol=6.99e-10` | correct |

**1 and 2** observed the whitespace-STRIPPED form while the real test observes
the spaced one. For Closure-62 the defect IS whitespace, so a check that
normalised it away rebuilt the scenario wrong — this is exactly the
Closure-62-c false-alarm class H3 was built for.

**3** stops at `here` and never reaches `assert (1;` — a genuinely shorter
output, so a genuinely different scenario.

**5** observed `4.94…` where the real test observes `0.257…` / `11.41…` —
different values, different scenario. And it cost nothing: Math-68 in that same
roll still has `crashed_on_patch=True`, so the catch survived the rejection.

## The one that is wrong — and its cause

Case **4** (Closure-62-c, July B):

```
  observed : '...error description here\nassert (1;\n expected=...'   (escaped)
  real     : 'ion here<newline>assert (1;'                            (literal)

  _values_match as recorded          : False   -> REJECTED
  _values_match with escapes decoded : True
```

**The harness observed the right content and spelled the newline as an escape.**
`_values_match` normalises whitespace, which cannot bridge a two-character `\n`
against a real newline, so a faithful harness was rejected on spelling.

## Why this is now urgent rather than historical

That rejection is from JULY, before 8.4 existed — some harnesses escaped
newlines on their own. **8.4 now REQUIRES it**: the prompt tells every
normalising check to emit `\n` and `\t` as two-character sequences so the alarm
stays on one line.

So the input shape that produced this one wrong rejection is now the *mandated*
shape for exactly the checks H3 polices — lifted, text-comparing checks on
formatted output. The rate of this error should be expected to rise, not stay at
one in 120 legs.

## Recommendation

**Decode escapes on both sides before comparing**, in `_values_match` — the same
one-line change `raw_value_vs_pinned` already makes for the same reason (8.4's
comparison decodes both sides so an escaped raw and an escaped source literal
meet as the values they denote).

This is a small, contained fix to a mechanism the audit classed KEEP, and it is
verdict-affecting, so it should be measured alone rather than folded into the 8.2
ladder.

**Not applied here** — 9.1 was scoped as a read, and this is a code change with
a guard requirement.
