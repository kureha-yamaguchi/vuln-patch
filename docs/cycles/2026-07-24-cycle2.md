## Spec G — muted per-check replay (the definitive shadowed-replay fact)

**Problem.** When a firing's buggy-side replay is shadowed (a different check throws first, or
the harness's own oracle throws before an escaped-crash site), the per-input fact "does THIS
check fire / does THIS crash occur on the buggy build?" is currently uncomputable — the honest
UNKNOWN note (cycle 1) leaves a vacuum the judge fills with stories. The harness source is
available; oracle throws are syntactically identifiable. Mechanically silencing the shadowing
throws and re-replaying computes the missing fact. No prompt/codegen change: this is a source
transform on already-generated Java.

**G-G1: the transform (pure, `src/java/execution/oracle_mute.py`).**
`mute_oracles(java_source: str, mute_ids: set|None = None, mute_all: bool = False) -> str`
- Silences every `throw` statement whose thrown constructor's FIRST string literal starts with
  `[oracle:<id>]` for `<id>` in `mute_ids` (or ANY oracle/alarm throw when `mute_all`,
  including `FuzzerSecurityIssue*` throws and `"relation <name> violated"`-style
  RuntimeExceptions — for relation-screen wrapper sources, `mute_ids` entries must also match
  the `relation <name> violated` message shape).
- Statement-aware, string-literal-aware scan: from the `throw` keyword to its terminating `;`
  at paren-depth 0 (concatenated multi-line messages must be handled). Replacement: a single
  `;` plus a trailing `/* muted:<id> */` comment.
- Pure function; no I/O. It MUST NOT touch non-alarm throws (library rethrows, input-rejection
  throws without an oracle tag).
- Known Java hazard: removing a guaranteed throw can break definite-return analysis (a
  non-void method whose all paths threw). The transform does not try to be clever about this —
  the compile step below catches it and the caller falls back gracefully.

**G-G2: the muted replay (`FuzzRunner.replay_input_muted` in fuzz_runner.py).**
`replay_input_muted(harness_path, class_name, project_cp, input_file, mute_ids=None,
mute_all=False, builder=None, buggy_dir=None, timeout_seconds=30) -> (status, fired_ids, output)`
- Reads the harness .java source, applies `mute_oracles`, writes the variant to a sibling
  `muted_<n>/` dir, compiles via the existing HarnessBuilder against the SAME project dir the
  original compiled against, replays the exact input, returns like `replay_input_report` plus
  status: `"crashed" | "clean" | "error" | "mute_failed"` (`mute_failed` = the muted variant
  did not compile — caller keeps the cycle-1 UNKNOWN/SHADOWED fact unchanged; never worse than
  today).
- At most ONE muted re-replay per judged firing (bounded cost).

**G-G3: wiring + facts (run.py call sites, note text in evidence_facts.py).**
1. Semantic shadowed branch (cycle-1 note "whether THIS check fires there is UNKNOWN"): after
   composing that note, run the muted replay with `mute_ids = breplay_ids` (the shadowing
   checks) on the BUGGY build. Outcomes, as a new pure builder
   `muted_replay_note(target_ids, muted_ids, status, fired_ids, esc_type, bt_all)`:
   - target check fires on buggy → the same-check family fact now applies at THIS input:
     "with the shadowing check(s) <ids> silenced, THIS check fires on the BUGGY build at this
     exact input — behaviour is identical on both builds; the patch did not cause this."
     (This is the identical-on-both-builds fact the MECHANICAL-FACTS rule makes binding.)
   - target check quiet, run clean → "with the shadowing check(s) silenced, the buggy build
     runs this exact input WITHOUT firing this check — the patch introduced the violation
     here" (the existence-proof wording family).
   - `error`/`mute_failed` → keep the cycle-1 UNKNOWN fact; append one line stating the muted
     replay was attempted and unavailable.
2. Differential-replay SHADOWED verdict (escaped crash behind oracles): re-replay with
   `mute_all=True` on the buggy build; compare exception-at-frame:
   - same exception type + frame as the patched crash → upgrade to PREEXISTING (existing drop
     path semantics, note says the crash site reproduces on buggy once the harness's own
     checks are silenced).
   - clean or different non-alarm crash → the INTRODUCED family fact, stated with the muted
     context.
   - `error`/`mute_failed` → keep SHADOWED as-is.
3. All new note text lives in evidence_facts.py (pure builders); run.py only computes inputs
   and prints.

**Fixtures (provenance: archived runs).**
- Transform: extract two REAL harness sources from trace.md `<harness>` blocks —
  (a) c1flag `02_*Math-30*` (multi-oracle, `[oracle:midpoint-pvalue]` etc.): mute one id →

- Note builders: target-fires → identical-on-both-builds wording; target-quiet-clean →
  existence-proof wording; mute_failed → UNKNOWN retained with one appended line.
- Compile/replay legs are VM-validated (c2flag run), not unit-tested.

## Spec H — fire-rate facts into the judge's evidence

**Problem.** The pipeline already computes the numbers that indict broken checks — buggy-side
screen ratio (checked/violated), patched-side replay-fuzz counts, and the screening demotion
reason for above-ratio relations — but they reach the judge unlabeled or not at all. A check
firing on a large share of RANDOM VALID inputs on the patched (or both) build(s) contradicts
known-good behavior broadly; that indicts the check, not the patch.

**Requirements.**
1. New pure builder in evidence_facts.py:
   `fire_rate_fact(buggy_checked, buggy_violated, patched_checked, patched_violated,
   screen_outcome_reason) -> str|None` — emits a "[fire-rate fact]" block with the raw counts,
   percentages, and interpretation guidance:
   - patched rate ≥ ~20%: "a contract violated by X% of random valid inputs on the PATCHED
     build indicts the check, not the patch — real defect discriminators fire rarely and
     asymmetrically; keep only with a shown contract that makes every one of those inputs a
     genuine violation."
   - buggy rate ≈ 100%: "fires on essentially every input on the buggy build — the firing is
     intrinsic to the check/setup construction, not a detection of the defect."
   - low/absent rates → return None (no noise).
2. Wire it into every judged RELATION-path firing (replay findings carry counts already;
   screening stats live on the relation's screen note/decision). When a relation was demoted
   `above-ratio-cap / inverted (replay-only)` at screening, that demotion reason MUST appear
   in the fact for any replay finding it produces.
3. No auto-drop anywhere in this spec — facts into evidence only (the never-auto-dismiss rule
   stands; the judge decides, but now against numbers).
4. Threshold constants live in evidence_facts.py with the existing MAX_FIRE_RATIO (0.20)
   referenced, not duplicated as a magic number.

**Fixtures.** Real numbers from archived traces: Math-65 (patched 9674/20000 ≈48%) →
indictment wording present; Chart-19 armA (buggy 20000/20000) → intrinsic wording; a
low-rate case (e.g. 285/20000 ≈1.4%) → None or neutral (no indictment wording).

## Spec I (cycle-2b hotfix) — "identical" requires a value comparison

**Problem (found by c2flag validation).** The same-check buggy-replay fact and the
muted-replay fires-on-both fact both claim "behaviour at this input is identical on both
builds" knowing only that the same check FIRED on both builds. Firing on both ≠ identical
values: a partially-unfixed overfit fires the same check on both builds with DIFFERENT
observed values (both wrong, differently). With the MECHANICAL-FACTS rule binding, the
over-claim mechanically dismisses genuine catches (c2flag Math-68: fr-1-rms fired
patched=4.9489 vs expected 6.9989, buggy also fired, values never compared → FN).

**Requirements.**
1. evidence_facts: `compare_fired_values(patched_msg, buggy_msg) -> "identical"|"different"|"unknown"`
   — extract observed numerics from both fired messages (reuse the actual=/got=/was= +
   trailing-number extraction), NaN-safe equality at the 1e-9-relative floor; "different"
   only when both sides have numbers and none of the patched observed values matches a
   buggy observed value; "unknown" when either side has none.
2. `semantic_buggy_replay_note` same-check/no-defect branch and `muted_replay_note`
   target-fires branch take the value verdict:
   - identical → current wording stands ("behaviour at this input is identical on both
     builds").
   - different → "the SAME check fires on BOTH builds but with DIFFERENT observed values
     (buggy: <msg-excerpt> vs patched: <msg-excerpt>) — the patch changed behaviour at this
     input without restoring the expected value: the partial-fix pattern; this firing
     remains evidence against the patch."
   - unknown → fires-on-both stated WITHOUT the word "identical"; keep the existing
     bug's-own-family keep/dismiss guidance.
3. run.py: extract the same oracle's fired message from the buggy replay output
   (`_breplay_out` / muted replay output) — the `[oracle:<id>] ...` line — and thread both
   messages through. Absent extractable message → "unknown".
4. Fixtures: Math-68 c2flag pair (different → partial-fix wording, no "identical");
   Math-30 NaN pair (identical → current wording); non-numeric pair (unknown → no
   "identical", guidance preserved).
