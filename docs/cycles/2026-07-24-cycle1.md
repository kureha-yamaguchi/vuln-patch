## Spec A — extract evidence-fact logic into a pure, testable module

**Problem.** The evidence facts handed to the soundness judge are built inline in `run.py`
(differential replay ~1764–1814; semantic buggy-replay note ladder ~2106–2330; trigger-test-lift
note ~2505–2536). Inline logic can't be unit-tested, which is why three wrong-fact bugs shipped.

**Requirement.** New module `src/java/relations/evidence_facts.py` containing pure functions
(no I/O, no subprocess, no LLM; inputs are primitives/sets/strings; outputs are
`(verdict, note_text)` or `note_text`):

1. `classify_differential_replay(patched_sig, buggy_status, buggy_sig) -> (verdict, note)`
   - `buggy_status` ∈ `{"crashed", "clean", "error"}` (see Spec B for where it comes from).
   - verdict ∈ `{"INTRODUCED", "PREEXISTING", "SHADOWED", "ABSTAIN"}`.
2. `semantic_buggy_replay_note(fired_ids, breplay_status, breplay_ids, bt_all, bt_defect,
   esc_type, idline) -> note | None` — a port of the existing branch ladder, with the
   shadowed-branch change of Spec C. All other branches keep their current wording verbatim.
3. `trigger_lift_note(lifted_names, generic_lift, value_verdict) -> note | None` (Spec D), plus
   helper `fired_value_vs_trusted(fired_msg, trusted_values) -> "matches" | "differs" | "unknown"`
   implementing the numeric comparison of Spec D.

`run.py` call sites are replaced by calls into this module; behavior must be identical except
where Specs B–D change it. No other `run.py` behavior may change. Keep the existing print lines
(they feed the trace); printing may stay at the call sites.

**Acceptance.** `uv run pytest tests/` passes; a grep shows the three note-text families are
generated only in `evidence_facts.py` (run.py contains no copies).

## Spec B — G1 part 1: a replay can't say "clean" when it errored or never arrived

**Problem 1 (error conflation).** `FuzzRunner.replay_input` returns `None` both when the buggy
replay ran to completion without crashing AND when the replay itself failed to run. The caller
then emits *"the exact firing input does NOT reproduce this crash on the buggy build …
the crash is introduced by the patch"*. An infrastructure error must never manufacture evidence
against the patch.

**Problem 2 (oracle shadowing).** The same "introduced by the patch" conclusion is emitted when
the buggy replay *did* crash — at the harness's own alarm (`FuzzerSecurityIssue*` or any
`[oracle:…]`-tagged throw) — while the patched-side firing is an escaped exception (no oracle
id). In that situation the buggy run died at a check *before ever reaching the code that crashed
on the patched build*: the comparison is uninformative, not exculpatory-for-buggy. (An accepted
harness fires on the buggy build by construction, so any harness statement placed after the
checks is structurally unreachable on buggy — this exact geometry produced a conviction of a
correct patch in all three arms.)

**Requirements.**
1. Add `FuzzRunner.replay_input_result(...) -> (status, sig)` with
   `status ∈ {"crashed", "clean", "error"}` (`sig` = crash_signature when crashed, else None).
   `replay_input` may remain as a thin wrapper for other callers.
2. `classify_differential_replay` verdicts:
   - `error` → `ABSTAIN`, note: replay unavailable, no attribution fact, judge sceptically.
   - `crashed` with `buggy_sig == patched_sig` → `PREEXISTING` (unchanged semantics: drop path,
     including the existing non-generic-sibling rescue).
   - `crashed` with buggy_sig a harness-own alarm (contains `FuzzerSecurityIssue` OR matches
     `[oracle:` id extraction) while the patched firing is an escaped exception → `SHADOWED`,
     note (exact intent, wording may be polished): *"differential replay SHADOWED: on the buggy
     build this exact input triggers the harness's own check `<buggy_sig>` before execution
     reaches the site that crashed on the patched build — the replay is uninformative about
     whether this crash pre-exists. Do NOT treat this as evidence the patch introduced the
     crash. If the crash site lies in harness code that only executes when all checks pass, the
     firing is a harness artifact that can only ever appear on a correct build."*
   - `crashed` with a different *non-alarm* signature, or `clean` → `INTRODUCED` (current
     wording), which is now trustworthy because clean really means "ran to completion".
3. The `SHADOWED` and `ABSTAIN` verdicts must not drop the finding mechanically — they attach
   the note and let the judge rule (consistent with the never-auto-dismiss-on-ambiguity rule);
   only `PREEXISTING` keeps its existing drop behavior.

**Fixtures (provenance: archived arm runs, `runs-archive/runs/`).**
- armA `05_*Closure-70*/trace.md` evidence block (~line 6690): patched
  `java.lang.IllegalStateException@com.google.common.base.Preconditions.checkState`, buggy
  `com.code_intelligence.jazzer.api.FuzzerSecurityIssueLow@…FuzzHarness.runOracle` →
  must yield `SHADOWED` (today: INTRODUCED — the wrong fact that convicted a correct patch).
- Synthetic: status `error` → `ABSTAIN` (today: INTRODUCED).
- Regression: identical escaped sig both sides → `PREEXISTING`; buggy `clean` → `INTRODUCED`;
  frame-less/missing-artifact abstains preserved.

## Spec C — G1 part 2: the shadowed semantic-replay branch must not extrapolate

**Problem.** When a *relation/oracle* firing is replayed on buggy and a DIFFERENT check fires
first (`_breplay_ids` non-empty, disjoint from `_fired_ids`), the current note tells the judge:
*"Rely on the screening/direction fact … a screening result of DIRECTION-CONFIRMED already
establishes the buggy build violates this check."* Direction-confirmation was established at
*screening inputs*, not at this firing input — this sentence licenses extrapolating a
confirmation from one input regime to a completely different one, and did so in two of the three
robust wrongful convictions.

**Requirement.** Replace that branch's note with (intent): *"on this exact input a DIFFERENT
check fired first on the buggy build (<ids>), so whether THIS check fires there is UNKNOWN — the
replay is shadowed, not confirming. The screening DIRECTION-CONFIRMED fact was established on
screening inputs, which may lie in a different input regime than this firing; it does NOT by
itself establish the buggy build violates this check at THIS input. With no per-input
attribution fact, judge on soundness alone, sceptically: to keep, the check's expected value
must be justified by a shown contract or trusted value that covers THIS input's regime."*
All sibling branches (same-check, defect-type, clean-handles, latent) keep current wording.

**Fixtures.**
- armA `08_*Math-30*/trace.md`: fired `{large-identical-p1}` vs breplay first-firing
  `{big-dataset-threshold}` → new note asserts UNKNOWN-at-this-input; must NOT contain
  "already establishes".
- armA `10_*Math-65*/trace.md`: fired `{chi-weighted-sum}` vs breplay `{circle-dense-err0}` →
  same.
- Regression: `_fired_ids & _breplay_ids` non-empty → current same-check wording unchanged;
  `breplay_status == "error"` → current unavailable wording unchanged.

## Spec D — G5: the trigger-test-lift note must compare values before it may say "dismiss"

**Problem.** `run.py` ~2505–2536: when a fired oracle's *name* matches `lift|seed[-_]?test` (or
lifts a trigger-test method), an evidence note is attached whose two branches both end in
dismissal: value matches the test → dismiss ("reproduced the test's scenario"); setup diverges →
also dismiss ("harness-setup divergence"). A divergent setup producing a value far from the
test's own is the *definition* of a generalization catch, and this wording killed one in the
run under study.

**Requirements.**
1. Compute a mechanical value comparison before wording the note:
   `fired_value_vs_trusted(fired_msg, trusted_values)`:
   - extract numeric literals tagged `actual=` / `got=` / `was=` (and bare trailing numbers)
     from the fired message; compare against each numeric trusted/lifted literal with the
     existing rounding floor (relative `1e-9`, `max(1,|a|,|b|)` scale);
   - any match → `"matches"`; numeric values present on both sides but none match → `"differs"`;
     no numeric values extractable on either side → `"unknown"`.
2. Note wording by verdict:
   - `matches`: current dismissal-leaning wording is fine (observed value IS the test's own
     scenario; test passes; dismiss).
   - `differs`: *"this oracle lifts <which>; the REAL test passes on this build, BUT the fired
     value differs from every value the test itself pins by more than the rounding floor — this
     is NOT a replay of the test's scenario; it is a candidate generalization catch beyond the
     test's inputs. Test-passage does NOT exonerate it. Judge its soundness on the shown
     contract/trusted values."* No occurrence of "must be dismissed".
   - `unknown`: neutral fact only (test passes; whether this firing replays the test's scenario
     is undetermined; judge on soundness), no "must be dismissed".
3. Name-regex detection may remain as a *detector* of lift provenance, but the dismissal
   instruction must never be attached on name evidence alone — only the value comparison
   licenses dismissal wording.

**Fixtures.**
- armC `11_*Math-68*/trace.md`: fired value `0.25781765926522887` vs the trace's trusted
  MINPACK literal (extract both, they differ by ~1.2e-5) → `differs` → keep-flavored note.
- armA `11_*Math-68*/trace.md`: oracle `jennrich-seed-p1` (no regex match) — regression: with
  lift undetected, no note; with detection widened, still keep-flavored.
- Synthetic: fired value equal to a trusted literal within 1e-12 → `matches` → dismissal wording
  allowed. Non-numeric firing (exception-only message) → `unknown` → neutral wording.

## Spec E — G5: fact-priority instruction in the soundness judge prompt

**Problem.** Twice in the studied run a mechanical fact stating identical behavior on both
builds was overridden by provenance narrative ("this assertion encodes the library's own trusted
regression test → SOUND"). Facts must outrank stories.

**Requirement.** In `relation_verifier.py`'s verify prompt (near the existing "OBSERVED EVIDENCE
BEATS HYPOTHETICALS" block), add one rule (intent): *"MECHANICAL FACTS OUTRANK PROVENANCE: a
bracketed computed fact ([buggy-replay fact], [differential replay], [trigger-test lift]) that
states the observed behavior is identical on both builds at the exact firing input, or that the
replay was shadowed/unavailable, can be overridden ONLY by another computed fact — e.g. a shown
trusted value or documented contract that covers the firing input's own regime. That a check
'encodes' or 'lifts' a trusted test is provenance, not a fact about THIS input: it never
overrides an identical-on-both-builds or shadowed fact by itself."* Keep it to one block; do not
otherwise reweight the prompt.

**Acceptance.** String-presence unit test (block present, placed after the observed-evidence
rule); no other prompt text changed (diff review).
